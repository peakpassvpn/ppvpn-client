# 需求与设计流程

需求、设计、缺陷和待办统一在 GitHub Issue 里管理。仓库只保存运行中系统的事实文档（`docs/architecture.md`、`docs/core-api.md`、`docs/host-integration.md`、`docs/release.md`、`docs/desktop/` 等），不再保存设计草稿；不要新建 `docs/drafts/` 或其它草稿目录。

## 什么时候开 issue

- 新需求、产品行为变化、架构调整：开 issue，设计写在 issue 里。
- 发现但这次不修的缺陷、技术债、待办：开 issue，写清现象、证据和影响。
- 当场修完的缺陷不需要先开 issue，PR 描述写清根因即可。
- 运营任务（宣传、发帖、公告、个案客服处理）不开 issue。issue 只管理需要改代码、配置、构建或发布流程的工作。
- 开之前先 `gh issue list --search "<关键词>" --state all` 查重。已有 issue 就在原 issue 上补充，不另开。

本仓库公开。issue、PR 和评论同样受 [`CONTRIBUTING.md`](../CONTRIBUTING.md) 的敏感信息规则约束：不写真实姓名、内部主机和地址、测试账号，日志先脱敏。

## issue 里写什么

标题写要达成的结果或观察到的问题，不写“设计”“草稿”“讨论”之类的词。正文按需取用下面几节，不要求固定模板：

- **背景**：现状、问题、证据（工单号、日志片段、代码位置 `path:line`、CI 运行链接）。
- **目标**：要达成的可观察结果和范围；明确不做的部分。
- **方案**：选定的做法、影响的契约（Core API、宿主接口、更新源、并发、失败处理、兼容已发布版本）、取舍。
- **待决**：需要用户拍板的业务或产品问题，每条附建议。
- **验收**：怎样算完成，对应哪一层测试（[`testing.md`](./testing.md) 的 L1、L2、L3），是否需要真机或发版验证。

设计变化时直接编辑正文，让正文始终是当前结论；讨论过程和决定记录写在评论里（“决定：…（用户，10-18）”）。不要在仓库里另写一份设计文档。

## 标签

每个 open issue 带一个类型标签、一个状态标签，以及一到两个领域标签。

| 类型 | 含义 |
|---|---|
| `bug` | 现有行为不符合预期 |
| `enhancement` | 新功能或行为变化 |
| `chore` | 技术债、测试、CI、运维、文档 |

| 状态 | 含义 |
|---|---|
| `needs-decision` | 有业务或产品问题等用户拍板，正文“待决”一节列出问题和建议 |
| `ready` | 目标和方案已定，可以开工 |
| `blocked` | 被其它 issue、外部依赖或发版卡住，正文写明卡在哪里 |
| `on-hold` | 主动搁置，正文写明恢复条件 |

| 领域 | 范围 |
|---|---|
| `area:core` | ppvpn-core、Sail 引擎、路由、DNS、TUN、隧道宿主 |
| `area:desktop` | 桌面客户端（Flutter 桌面）、特权 service、桌面更新 |
| `area:mobile` | iOS、Android 应用，网络扩展和 VpnService |
| `area:release` | CI、发布流水线、签名、公证、更新源、应用商店 |
| `area:account` | 账号、登录、团队、会话、权限、访问后端 |
| `area:notification` | 推送（APNs、FCM）、消息中心 |

Flutter 界面在桌面和手机共用；只影响一端的问题标那一端，两端都受影响就两个都标。

技术细节能当场判断的由维护者决定；只有业务规则、产品取舍、花钱、发版时间和对已发布版本有影响的改动才标 `needs-decision` 交给用户。用户拍板后在评论里记录决定，改正文，状态改为 `ready`。

## 开工到关闭

1. 开工前读 issue 正文和评论，在评论里写一句开工的分支名，避免两人同时做同一件事。
2. 从 `main` 拉分支，向 `main` 提 PR（见 [`release.md`](./release.md) 的“分支与版本”）。PR 描述写 `Closes #<编号>`（只完成一部分时写 `Refs #<编号>`）。
3. 实现完成后重读 issue 正文，确认每条设计承诺都落实到运行逻辑。长期有效的行为、架构和运维说明写进对应的事实文档，和代码在同一个 PR 里提交。
4. PR 合入 `main` 后 issue 自动关闭。只做了一部分时，在 issue 里写清剩余部分，或拆成新 issue。需要发版或真机验证才算完成的，合入后保持打开，验证通过再关。
5. 决定不做的 issue 写明原因后关闭（Close as not planned）；重复的标 `duplicate`，指向保留的那个后关闭。

## 整理

定期整理一次：关闭已在 `main` 实现或已过时的 issue，合并重复项，补齐标签，把长期 `blocked` 或 `on-hold` 的恢复条件重新核对一遍。

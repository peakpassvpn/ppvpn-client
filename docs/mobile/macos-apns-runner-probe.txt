Real macOS OS-token feasibility probe — builder execution contract

This is the executable first stage of macos-real-apns-acceptance.txt, not
another mock test. It does not require a DB lease, p8, login, Worker or send.
The diagnostic .app uses the frozen production ApplePushState.swift and
macOS ApplePush.swift receiver unchanged, a real AppKit application delegate,
the existing exact desktop AppID, production APNs profile and real Developer
ID signer. The real NSApplication registration callback supplies the token to
the production receiver. The token stays in process memory; only fixed native
receipts are exported. No fixed/pasted/mock token or direct didRegister call
exists in this diagnostic host. No Flutter, forwarding core, proof store,
credentials or additional auth namespace is linked. It never requests alert
permission, so it does not pass the later notification consent/UI gates.

Execution behavior / output
The real-run helper checks GitHub-hosted Mac context, console uid/GUI launchd
session, fresh PPVPN data/process/Agent absence, staged path and reviewed hashes.
It repeats the real signing verifier, starts unified-log Info capture BEFORE
LaunchServices opens the exact App, and accepts only exact native subsystem,
category, reviewed process image and newly observed source PID. A nonempty
token callback only counts after register_requested in that SAME process.
This is actual OS registration, not authorization to send or proof of delivery.
LaunchServices return0 is recorded separately from observed app launch.
The helper retains only typed fixed receipts/counts/status/hash metadata in a
new0600 result. No token/nonce/IDs, raw error text, profile/certificate bytes,
credential contents, host/user identifiers or raw log stream is exported.
It terminates only its log-capture child and newly launched exact-image App
in this fresh VM, never pkill/bootout/service/VPN/Surge or settings operations.

Result meanings
- OS_TOKEN_CALLBACK_OBSERVED: real OS callback nonempty in the same process as
  its observed request. Backend bind/register, real send/delivery and UI remain
  NOT RUN. No permission prompt was requested by the diagnostic host.
- OS_REGISTRATION_ERROR_OBSERVED: actual failure callback; report its fixed
  domain class and numerical code from native receipts. Root can diagnose that
  exact entitlement/network/OS condition. Unknown raw domains stay other.
- TIMED_OUT_NO_VERIFIED_OS_TOKEN_CHAIN: timed out without the full trace chain.
  Could be log availability, AppKit launch or OS registration; not universal
  VM/APNs incompatibility. Do not label a timeout as a provider rejection.
- Named preflight/LaunchServices/log-capture failure: actual missing capability,
  no token outcome claimed. Preserve its sanitized status, not a fabricated
  error. No physical fallback request until root reviews this actual evidence.

Upload only the sanitized result, source-build manifest and safe signing-check
